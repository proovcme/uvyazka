# DigUp: разбор кода и применение в Увязке

Проверено 25.10.2026. Исследован снимок
[`d6f1f480427d151640196e4d6588906e1f3ee782`](https://github.com/ARahim3/DigUp/tree/d6f1f480427d151640196e4d6588906e1f3ee782).
Это разбор исходников, контрактов и ограниченные расчётные наблюдения.
DigUp, EmbeddingGemma и Swift-тесты на Легионе не запускались; Swift CLI
не найден в PATH. Код DigUp в поставку Увязки не перенесён.

**Вывод:** полезен отдельный необязательный поставщик эмбеддингов и выбранные
решения индексатора. Поиск, адреса источников и инженерную память Увязки
нужно сохранить. Готовность интеграции и качество на ПД/РД не подтверждены.

## Как устроен

Папки обходятся crawler-ом; platform-читатели готовят текст и изображения.
Indexer передаёт их Embedder-у, сохраняет сегменты, FTS5 и векторы в SQLite.
Searcher сравнивает запрос с векторами, добавляет точные совпадения и
выбирает адрес фрагмента. На Windows/Linux интерфейс Tauri вызывает
Swift-процессы. Python/MLX worker — отдельный эталонный путь для сравнения,
его нельзя считать готовым Windows-бэкендом.
[Состав сборки](https://github.com/ARahim3/DigUp/blob/d6f1f480427d151640196e4d6588906e1f3ee782/Package.swift).

Системы различаются: Windows использует PDFium и portable-читатели,
macOS — собственные фреймворки. Прямого MCP-контракта в изученных CLI и
сервисах нет; есть JSON lines поверх stdin/stdout.

## Что стоит использовать

| Решение | Применение |
|---|---|
| Объединение смыслового и точного поиска | Свободная формулировка помогает найти кандидата, марка/ID остаются точными поисковыми признаками |
| Текст и изображения в одном пространстве | Искать также сканы и графические фрагменты, затем открывать оригинал для чтения |
| Отдельный процесс эмбеддингов | Поиск остаётся локальным инструментом; основной ИИ работает в выбранном MCP-клиенте |
| Отложенное чтение длинных файлов | Рано давать первые результаты, сохранять остаток и продолжать после остановки |
| Версия векторного пространства и контрольные векторы | Обновление runtime не должно незаметно смешивать несовместимые индексы |
| SQLite, компактные векторы и освобождение памяти | На первом этапе можно обойтись без отдельного сервера векторной базы |
| Замеры на машине и журнал этапов | Оценивать фактическую скорость, показывать ход работы и причины остановки |

### Поиск и масштаб

Используется полный перебор матрицы 768-мерных векторов, хранящихся в float16;
вычисление выполняется с преобразованием блоков в float32. Это не ANN-индекс.
Матрица 100 000 векторов занимает около 146,5 MiB без служебных структур.
Скорость на Легионе не измерена.
[Vectors.swift](https://github.com/ARahim3/DigUp/blob/d6f1f480427d151640196e4d6588906e1f3ee782/Sources/DigUpKit/Vectors.swift).

Векторные оценки центрируются по модальностям и нормируются по распределению
запроса. По умолчанию смысловой кандидат проходит при z >= 2; лексический —
при совпадении хотя бы половины выделенных слов. Числовые/буквенно-цифровые
запросы получают больший вес точного поиска. Это эвристика ранжирования,
а не вероятность правильного ответа или инженерный допуск.
[Searcher.swift](https://github.com/ARahim3/DigUp/blob/d6f1f480427d151640196e4d6588906e1f3ee782/Sources/DigUpKit/Searcher.swift#L116).

Аналитический пример для одной модальности: сходства 0,9 и 0,8 дают z около
1 и -1. Без совпадения слов оба не проходят порог 2. Для четырёх сходств
0,9/0,8/0,8/0,8 максимум z около 1,73. Поэтому порог нельзя переносить
неизменным на маленький или однородный проектный индекс.
Это расчёт по формуле исходника, не результат работы модели.

## Что нельзя переносить без изменения

| Найденное поведение | Почему важно для ПД/РД | Требование к адаптеру |
|---|---|---|
| Лучший фрагмент выбирается на файл | Несколько подходящих листов одного тома могут схлопнуться в один результат | Возвращать несколько независимых сегментов одного документа; группировать только в UI |
| В sync изменение определяется размером/mtime, перенос — также inode/device | Замена байтов при прежних метаданных не даёт доказательства актуальности | Использовать зарегистрированный SHA-256 и версии источников Увязки |
| В portable PDF-ветке нет OCR | Вектор картинки не даёт буквального текста и чисел скана | Сохранять наш OCR и независимое чтение оригинала |
| При достаточном тексте страница идёт текстовым маршрутом | Текст штампа не описывает всю графику чертежа | Для чертежей сохранять текст и изображение/области одновременно |
| Вектор PDF строится по первым 4000 символам страницы | Содержание дальше этого префикса не представлено в её текстовом векторе; полный текст остаётся в FTS | Делить длинные страницы с адресами и показывать полноту индексирования |
| Изображение страницы уменьшается под бюджет | На большом листе мелкие марки могут терять различимость | Индексировать виды и области с координатами, сохранять полноразмерный оригинал |
| Office-таблицы превращаются в последовательный текст | Формулы, A1-адреса и объединения не сохраняются как структура; пустые ячейки не удерживают позиции | Передавать наш адресный структурный слой и контекст заголовков |
| После ошибки позднего чтения длинный файл может получить done с пояснением | Состояние обработчика не равно полноте проверки | Хранить непрочитанный остаток отдельно от завершения задачи |
| Русские проектные обозначения не имеют отдельной настройки поиска | Porter и правила префиксов не обеспечивают русскую морфологию или различение похожих марок | Проверить кириллицу/латиницу, дефисы, ё/е и значимые цифры без опасной склейки обозначений |

Основания:
[sync и подготовка/сохранение PDF](https://github.com/ARahim3/DigUp/blob/d6f1f480427d151640196e4d6588906e1f3ee782/Sources/DigUpKit/Indexer.swift),
[portable PDF](https://github.com/ARahim3/DigUp/blob/d6f1f480427d151640196e4d6588906e1f3ee782/Sources/DigUpKit/Platform/Portable/PDF%2BPortable.swift),
[OfficeText](https://github.com/ARahim3/DigUp/blob/d6f1f480427d151640196e4d6588906e1f3ee782/Sources/DigUpKit/OfficeText.swift#L94),
[правила текста](https://github.com/ARahim3/DigUp/blob/d6f1f480427d151640196e4d6588906e1f3ee782/Sources/DigUpKit/SearchText.swift).

Дополнительно: страницы и документы, похожие на числовые данные без достаточной
прозы, могут не получать текстовый вектор. Для Увязки это нельзя превращать
в исключение количеств из индекса: строке нужны её наименование, заголовки,
единица, система и адрес. Смысловые кандидаты не заменяют точный поиск чисел.
Профили СПДС, разрешение сущностей и расчётные проверки DigUp не предоставляет.
Старый DOC в portable-ветке не читается, бинарный XLS также не поддержан
этим Office-читателем. Нативных RVT/DWG-читателей в рассмотренном наборе нет.
Поэтому новый поисковый слой не закрывает эти пробелы извлечения данных.

### Размер изображения

При стандартном pageBudget=280 изображение сначала рендерится в пределах
1400 px, затем приводится к бюджету энкодера с шагом 48 px. Для пропорций
крупного листа около 2,12:1 получается примерно 1152 × 528 px.
Проверка геометрии пяти локальных страниц показала, что условный текст
высотой 3 мм на одном из больших листов соответствовал бы примерно 2,7 px.
Это оценка масштаба при изображении целого листа, не измерение качества поиска.
[ImageSizing.swift](https://github.com/ARahim3/DigUp/blob/d6f1f480427d151640196e4d6588906e1f3ee782/Sources/LlamaRuntime/ImageSizing.swift).

## Runtime и контроль версий

В снимке закреплены GGUF Q8_0: текстовый файл 309 855 456 байт и media-файл
554 821 024 байт, всего 864 676 480 байт. Ревизия и SHA-256 заданы явно.
[ModelFiles.swift](https://github.com/ARahim3/DigUp/blob/d6f1f480427d151640196e4d6588906e1f3ee782/Sources/DigUpKit/ModelFiles.swift).

llama.cpp закреплён на commit `4d756bc72bf00a4aacf410ae15a2d315f3db400d`
(b11461), с небольшим патчем отключения ненужного выделения logits.
Это часть конкретной сборки; патч нельзя механически применять к другой версии.
[Сборка](https://github.com/ARahim3/DigUp/blob/d6f1f480427d151640196e4d6588906e1f3ee782/scripts/build-llama.sh).

У DigUp есть `vectorVersion` и эталонные входы/векторы; reference-тест требует
сходства не ниже 0,999. При изменении пространства индекс пересоздаётся либо
выдаётся ошибка. Эти тесты требуют весов; обычный CI явно их пропускает без
модели. Наличие теста не подтверждает его успешный запуск для каждого релиза.
[ReferenceVectorTests](https://github.com/ARahim3/DigUp/blob/d6f1f480427d151640196e4d6588906e1f3ee782/Tests/LlamaRuntimeTests/ReferenceVectorTests.swift),
[CI](https://github.com/ARahim3/DigUp/blob/d6f1f480427d151640196e4d6588906e1f3ee782/.github/workflows/ci.yml).

В изученном runtime лимит входа — 2048 токенов, а у `--text-only` — 512:
этот режим предназначен прежде всего для запросов. Он не подходит для
произвольной индексации длинных текстов без контроля усечения.
Это ограничения реализации DigUp; у EmbeddingGemma 2 заявлен контекст 8192.
Хранение готовых нормированных векторов в float16 не означает вычисление
самой модели в float16: карточка модели отдельно предупреждает об этом режиме.
[LlamaEmbedder.swift](https://github.com/ARahim3/DigUp/blob/d6f1f480427d151640196e4d6588906e1f3ee782/Sources/LlamaRuntime/LlamaEmbedder.swift#L60),
[карточка модели](https://huggingface.co/google/embeddinggemma-2#4-numerical-precision).

## Предлагаемая связка

```text
Папка проекта → читатели Увязки → общая база источников и структуры
                                      ↓
                         текст / строки / изображения областей
                                      ↓
                         необязательный embedding-процесс
                                      ↓
                          производный индекс этого проекта
                                      ↓
                    точный + смысловой поиск через MCP и панель
                                      ↓
                   модель читает оригинал → сохраняет разбор/проверку
```

Первый эксперимент — адаптер к `digup worker`, а не перенос всего приложения.
Процесс принимает JSON lines с `id`, `op=text|image`, `inputs`, бюджетом
изображения. Ответ содержит размерность, base64 float32 little-endian,
ошибки отдельных входов; при старте — сведения о модели/runtime.
Это отдельный протокол, не MCP. Нужен наш адаптер с таймаутами,
проверкой размерности/конечности/числа векторов и обработкой остановки.
[WorkerService.swift](https://github.com/ARahim3/DigUp/blob/d6f1f480427d151640196e4d6588906e1f3ee782/Sources/digup/WorkerService.swift).

Для работы нужны helper и его DLL-зависимости, веса и проверенный runtime;
одного exe может быть недостаточно. В Windows-сборке используются Swift,
Rust, C/C++ и отдельные библиотеки. Перенос Python/MLX worker из репозитория
этого не устраняет. Сначала стоит оценить готовый helper в изолированном
прогоне, затем решить, оставлять его или делать более узкий native-worker.

Минимальный ключ производного индекса:

`project_id + doc_id + source_sha256 + locator + segment_hash + reader_version
+ chunker_version + model_revision + runtime_vector_version + dimension
+ prompt_version + image_preprocessing_version`.

В записи результата нужны адрес исходника, модальность, полнота, причины
усечения/ошибок и раздельные показатели точного и смыслового поиска.
Должно возвращаться несколько сегментов одного документа. Смена embedding-модели
пересчитывает производный индекс, сохраняя наблюдения и разборы проекта.
Без runtime остаются точный поиск и адресное чтение; fallback показывается явно.
Основной ИИ-клиент не меняется, сервер генерации ответов не появляется.

## Что проверить до включения

В трёх сохранённых `evals/*.json` — 126 запросов: 37 synthetic, 48 multilingual,
41 code. Кириллических запросов и записей с пустым expect в этих файлах нет.
Это не означает отсутствия отдельных unit-тестов отрицательных случаев,
но инженерный русский корпус этими evals не подтверждён.
[Наборы запросов](https://github.com/ARahim3/DigUp/tree/d6f1f480427d151640196e4d6588906e1f3ee782/evals).

Наш контрольный прогон должен включать:

1. Эталонные адреса страниц/ячеек для русских запросов и формулировок смежников.
2. Похожие марки, позиции и ID, различающиеся цифрой, дефисом или алфавитом.
3. Сканы, большие чертежи, несколько видов/масштабов, таблицы с объединениями.
4. Несколько правильных страниц одного PDF, данные после 4000 символов,
   малый индекс и длинный документ с незавершённым обходом.
5. Запросы без ответа: «ничего не найдено» отдельно от «ещё не прочитано».
6. Замену байтов при прежних размере/времени, новую ревизию модели,
   остановку процесса, возобновление и разделение проектов.

Сравнивать literal baseline, text hybrid и text+image hybrid по точному
адресу в top-k, пропускам, ложным результатам, скорости, RAM и размеру кеша.
Числовые пороги приёмки определить до прогона. Обещать улучшение качества
или переносить авторские показатели скорости до такого сравнения нельзя.
