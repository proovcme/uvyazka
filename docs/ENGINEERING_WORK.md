# Инженерные расчёты и оформление через MCP

Увязка предоставляет локальные числовые операции, хранение расчётных дел,
формирование PDF и адресную проверку оформления. Методики
[ru-aec](../skills/aec-engineering-work/references/ru-aec-methods.md) определяют
постановку и порядок инженерной проверки. API модели не нужен для работы ядра.
Новый навык [aec-engineering-work](../skills/aec-engineering-work/SKILL.md)
связывает методики с инструментами. Для PDF требуется extra readers/all с PyMuPDF.

## Операции

| MCP | Результат |
|---|---|
| list_engineering_methods | Десять методов, точные поля, единицы, области допустимых значений, ограничения и закреплённые ссылки ru-aec |
| run_engineering_calculation | Новый расчёт или исправленная версия; исходные данные, промежуточные действия, сравнения с чужим итогом, проверка явных критериев |
| get_engineering_work | Полные данные конкретного дела или список; история, актуальность исходников и зависимых расчётов |
| engineering_document_schema | Контракты реквизитов, листов, примитивов, УГО и проверок PDF |
| build_engineering_document | PDF расчёта и/или векторных листов, редактируемое описание, манифест; оригиналы не изменяются |
| check_engineering_document | Проверка фактических байтов PDF по указанным страницам и требованиям с сохранением результата |

Поддержаны: сумма произведений; заряд АКБ по двум последовательным режимам с
явными напряжениями и коэффициентами; прямое свободное звуковое поле; ток по
входной активной мощности; падение напряжения одного участка; расход жидкости
по тепловому балансу; потери участка по Дарси–Вейсбаху с заданными коэффициентами;
объём зоны и отношение открытой площади к объёму; портовая ёмкость с резервом;
равномерность освещённости по готовым значениям. Это отдельные математические
постановки, а не расчёт всех систем здания. Точные ограничения возвращает каталог.

Числа передаются как `{value, unit}`; единицы проверяются и приводятся.
Пропуск, NaN, бесконечность, неверная размерность и недопустимый диапазон
отклоняются. Численное ядро использует конечные числа двойной точности;
округление количества портов — точные дроби. Сравнение чужих итогов требует
явного абсолютного допуска; нормативный предел требует основания применимости.
Само вычисление это основание не проверяет. Произвольный исполняемый код не принимается.

## Синтетический пример

После выбора project_id запрос run_engineering_calculation:

```json
{
  "project_id": "demo",
  "calculation_id": "feeder-current",
  "title": "Синтетический пример тока",
  "method": "electrical_current",
  "inputs": {
    "input_power": {"value": "12", "unit": "kW"},
    "voltage": {"value": "400", "unit": "V"},
    "power_factor": {"value": "0.8", "unit": "1"},
    "phases": 3
  },
  "basis": "Демонстрация симметричной трёхфазной нагрузки",
  "assumptions": ["Все исходные значения синтетические"],
  "reported_results": {
    "current": {"value": "21.7", "unit": "A", "tolerance": {"value": "0.1", "unit": "A"}}
  },
  "request_id": "demo-current-1"
}
```

Результат около 21,65 A. Это не подтверждение сечения кабеля и выбора защиты.
Для реального документа вместо вымышленных исходных данных укажи sources:
doc_id, sha256, reason и при наличии физический page_number PDF. Ссылка
фиксирует исходник; правильность переноса значения устанавливает читающий.
Исправление требует expected_revision и reason. Старая версия сохраняется;
изменение исходных байтов отмечает её как неактуальную. Повтор того же запроса
с тем же request_id не создаёт вторую версию.

Для PDF расчёта передай build_engineering_document идентификатор и версию
расчёта в calculations, title, basis, request_id и metadata с designation,
project, stage, organization. Необязательные developer/checker — имена,
подписи не создаются. Листы pages задаются в миллиметрах от левого верхнего
угла, A4 или A3; доступны линии, прямоугольники, окружности, текст и вставки
символов. Для каждого используемого символа нужны геометрия, подпись и
происхождение; его изображение и пояснение попадают в легенду того же листа.
Выход за рабочую область и переполнение текстового поля отклоняются.

## Границы оформления и проверки

Рабочий макет engineering-review-layout-v1 имеет рамку и упрощённый блок
реквизитов. Он не реализует полностью нормативную форму основной надписи,
специальные формы каждой дисциплины и чертёжный шрифт по ГОСТ. Перед выпуском
нужна применимая форма и проверка конечного отпечатка. Генератор создаёт
векторный PDF и описание, нативные DWG/RVT не редактирует. Существующие
инструменты спецификаций и нативного чтения остаются отдельными операциями.

check_engineering_document принимает зарегистрированный PDF с sha256 либо
точную версию сформированного документа, 1–10 физических страниц и 1–40 правил
с basis. Поддержаны размер страницы, нативная векторная рамка, минимальный
размер шрифта PDF в пунктах и обязательный текст в заданной области.
Составной контур рамки проверяется по полному покрытию четырёх сторон.
Координаты относятся к невращённой странице PDF. Размер шрифта PDF не равен
измеренной высоте прописной буквы. Отсутствие текстового/векторного слоя
и неизвестные правила дают unchecked. Оставшиеся страницы указаны отдельно.
Смысл УГО, все графы штампа, подписи и полнота нормативной проверки не утверждаются.

Расчёты и проверки хранятся в общей базе проекта с неизменяемой историей.
PDF и описание находятся в engineering-exports данного проекта. Изменённый PDF
не принимается за прежний результат. Исправление расчёта отмечает зависимый
документ как требующий пересмотра; проверка старого документа не превращает
его в актуальный выпуск. Все результаты имеют accepted=false.

Проверено синтетическими числовыми задачами, фактическим чтением сформированных
PDF и официальным MCP stdio-клиентом с перезапуском сервера. Приёмка новых
операций в каждом настольном клиенте и полный нормоконтроль не заявляются.
