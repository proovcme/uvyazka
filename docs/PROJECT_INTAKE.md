# Единый приём проекта

Модель через MCP и человек через локальную панель используют один сервис
приёма и одно хранилище `UVYAZKA_HOME`. Каждый проект сохраняет существующую
базу `projects/<project_id>/project.sqlite3`: источники, наблюдения, версии,
сопоставления, измерения и инженерный граф. Журнал приёма находится в общем
реестре `registry.sqlite3` и ссылается на тот же project_id.

## Вход через модель

Пользователь явно передаёт папку и разрешает её разбор. Модель вызывает:

```json
{"source_root":"C:\\Projects\\Building", "name":"Здание"}
```

Это аргументы `import_project_folder`; project_id можно передать явно или
получить из результата. Сохраняются intake_id и project_id. Чтение запускается
в фоне, исходники не меняются. `get_project_intake(intake_id=...)` показывает
этап, текущий документ, время обновления, журнал и покрытие. После ready/partial
модель продолжает через project_status, find_documents, read_evidence и
record_observations. Для одинакового разрешённого пути используется уже
зарегистрированный проект, включая проект, добавленный в интерфейсе.

Повторное подключение папки сохраняет наблюдения и запускает инкрементальное
чтение. Новый хеш или версия читателя создают новое извлечение; прежние
источники и наблюдения остаются доступными по своим версиям. Совпадение пути
не определяет действующую проектную ревизию.

## Вход через человека

Запустить `uv run uvyazka dashboard` и открыть локальную панель. Кнопка
**«Добавить проект»** доступна и при пустом хранилище. На странице три способа:

- **Папка на компьютере:** указать полный путь. Чтение идёт по исходному
  пути без копирования. Этот же путь можно передать модели через MCP.
- **Выбрать папку:** браузер передаёт копию файлов с вложенными каталогами.
- **Архив ZIP:** передаются байты, затем проверяются имена и распаковывается
  структура. Другие архивные форматы в этой версии не поддержаны.

Копии хранятся в `intakes/<intake_id>/sources`. При копировании локальная
папка пользователя и её копия — разные источники: автоматическое объединение
по похожим именам или совпадению части файлов не выполняется. Для дальнейшей
работы выбирают полученный project_id. MCP видит его через list_projects.
Повторный приём нового архива создаёт отдельный проект; обновление состава
существующего проекта загружаемым архивом — отдельная будущая операция.

В обоих входах используется общий буквальный читатель PDF, DOCX, XLSX/XLSM,
CSV/TSV, TXT/Markdown. Остальные файлы входят в реестр с явным статусом;
RVT/DWG/IFC требуют соответствующего модельного инструмента. Скан с малым
объёмом текста остаётся сигналом для просмотра и адресного OCR. Приём не
создаёт инженерные показатели по догадке и не запускает отдельную LLM.

## Состояние и продолжение

Статусы: receiving → queued → extracting (ZIP) → indexing → ready/partial.
Failed содержит причину и журнал. Процент показывается только для реально
переданных байтов; чтение сообщает этап и документ без выдуманного процента.
Ready означает завершённое буквальное извлечение, partial — наличие
непрочитанных/пустых/неподдержанных источников или блоков с малым объёмом текста.
Смысловое покрытие и инженерное принятие оцениваются отдельно.

При передаче папки хранится манифест и хеш каждого полученного файла.
Неполная передача не публикуется как готовый проект. После перезапуска в
панели можно выбрать **«Продолжить передачу»**, снова выбрать тот же комплект
и повторить передачу. Состояние и сохранённые файлы не теряются; незавершённый
файл не подменяет целый файл. При передаче отдельного файла предыдущим
процессом может потребоваться дождаться истечения аренды.

Чтение возобновляется кнопкой в панели или `resume_project_intake(intake_id)`.
Общая аренда в SQLite предотвращает дублирование активного обработчика между
процессами. Живой обработчик продлевает её каждые 15 секунд. После аварийного
завершения продолжение доступно после истечения аренды, не позднее 90 секунд
от её последнего продления. Автоматический запуск обработки после старта
MCP/панели не выполняется: пользователь или модель явно продолжает приём.

Неудавшийся читатель не повторяется молча при каждом проходе и не блокирует
остальные документы. После исправления причины повтор вызывается с
retry_failed=true или кнопкой **«Повторить неудавшееся чтение»**. Успешные
неизменённые извлечения берутся из существующего снимка/кеша.

## Границы хранения и передачи

Панель показывает фактический каталог хранилища. MCP следует настроить через
`uvyazka client-config ...` с тем же --home/UVYAZKA_HOME; разные каталоги состояния
создают независимые рабочие среды. Запись из браузера требует loopback Host,
допустимого Origin и сессионного токена. Сервис не принимает внешние URL.

Размер входного файла ограничивается свободным диском, а не произвольным
лимитом загрузчика. Действуют отдельные существующие пределы читателей
(например, 64 MiB для буквального PDF/Office). Их отказ виден в покрытии и не
удаляет исходник. Манифест ограничен 100000 файлами, ZIP — 100000 записями;
это защита ресурсов, а не обещание полной обработки любого архива.

ZIP проверяется до извлечения: пути вне каталога, специмена Windows, потоки
NTFS, ссылки, специальные файлы, зашифрованные записи, дубли имён с учётом
регистра и конфликты файла/каталога отклоняются. Проверяются CRC при чтении и
хеш архива до регистрации проекта. Файлы из проекта не исполняются.

## Проверка реализации

Синтетические тесты проверяют HTTP → общий сервис → память → продолжение
моделью и обратное чтение через HTTP; официальный MCP stdio с перезапуском;
параллельную регистрацию одного пути; просроченные аренды; незавершённую
передачу; сохранение истории; опасные ZIP. Эти проверки не подтверждают
визуальную приёмку интерфейса или установку в конкретном ИИ-клиенте.
