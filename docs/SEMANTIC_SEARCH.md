# Локальный поиск по смыслу

Увязка использует необязательный `digup worker` для эмбеддингов. Документы
читают прежние читатели Увязки, адреса и производный индекс остаются в общей
SQLite проекта. Ответ формирует модель в вашем ИИ-клиенте. API генерации,
чат с локальной моделью и загрузка документов во внешний сервис не нужны.

## Установка на Windows

Из корня установленной Увязки, в её Python-окружении:

```powershell
python tools/setup_embeddings.py --home C:\ProjectMemory
```

Нужен 7-Zip; можно указать `--seven-zip`. Скрипт скачивает около 906 MB:
закреплённый Windows x64 релиз DigUp 0.7.0-beta.3 и два Q8_0 GGUF. Проверяет
SHA-256, извлекает helper с лицензиями, приложение DigUp не устанавливает.
Источник весов: `ggml-org/embeddinggemma-2-GGUF`, ревизия
`bfcd298762cc34d0357ece5ebdd31791a3a374d8`. Модель EmbeddingGemma 2,
размерность 768. Входной тип Q8_0, хранение выходных векторов Float16.
Скрипт обращается к GitHub/Hugging Face только за runtime и весами.

Для уже подготовленного runtime:

```powershell
uvyazka --home C:\ProjectMemory configure-embeddings --executable C:\EmbeddingRuntime\helper\digup.exe --models C:\EmbeddingRuntime\models
```

Пути записываются в частный `embedding-worker.json` внутри home. Выбор
исполняемого файла выполняется локально; содержимое проекта, веб-страница
и MCP-запрос не могут поменять команду. Панель и MCP должны использовать
один home. Без настройки точный поиск работает самостоятельно.
`pip install '.[search]'` добавляет необязательный NumPy для ускорения
сравнения векторов; без него используется stdlib.

## Использование

В панели откройте **«Поиск в проекте»**. Запрос выполняется кнопкой «Найти».
Режимы: точный, по смыслу, совмещённый. «Подготовить индекс» обрабатывает
порции до 12 фрагментов; видны время, готовые, ожидающие и неудачные записи.
Остановка происходит после текущей порции. Завершённые записи сохраняются.

В MCP:

1. `get_semantic_search_status(project_id)` — конфигурация и состояние без
   запуска модели.
2. `build_semantic_index(project_id, limit=24, doc_ids=[...])` — до 64
   фрагментов за вызов. Повторять до обработки выбранного состава. Для
   повторения неудачных записей передать `retry_failed=true`.
3. `search_project_memory(project_id, query, mode="hybrid")` — несколько
   адресных фрагментов, в том числе одного документа. `doc_id` ограничивает
   область до ранжирования. Старый `search_project` сохраняет прежний контракт.

Сначала нужны зарегистрированные источники и сохранённые текстовые блоки.
Индексирование не запускает скрытое повторное чтение всего архива. Для скана
можно сохранить OCR через существующий инструмент либо явно выделить вид
через `save_drawing_view`. Растровые области индексируются отдельным image
worker-путём. Автоматического обнаружения всех видов/таблиц/сканов здесь нет.

## Что связывает автоматику и модель

```text
Источники → читатели Увязки → pages / chunks + локаторы в SQLite
                              ↓                    ↓
                       точный поиск          адресные сегменты
                                                   ↓
                                         локальный DigUp worker
                                                   ↓
                                       semantic_vectors в той же БД
                              ↓                    ↓
                         search_project_memory / панель
                                      ↓
                           чтение оригинала человеком/ИИ
                                      ↓
                       наблюдение, разбор или вопрос с источником
```

Текст делится по UTF-8 бюджету до 1000 байт с перекрытием; сохраняются исходные
символьные смещения и локатор блока: физическая страница PDF, строка Excel,
таблица/абзац DOCX. Подготовленные виды PDF сохраняют страницу, область в
неповёрнутых PDF points, ID и ревизию вида. Рендер ограничен 1600 px и image
budget 560. Описательный угол вида не изменяет координаты исходника.

Ключ индекса включает источник, SHA-256, ревизию читателя, смещения/вид,
версию сегментации и prompting. Векторное пространство включает сведения
worker и фактические SHA-256 весов, executable и соседних DLL при запуске.
Изменение модели создаёт новое пространство; смешивать старые и новые
векторы нельзя. Инженерные наблюдения и разборы не меняются.

Готовность в статусе относится к зарегистрированным версиям. Перед выдачей
каждого документа проверяются реальные байты источника; замена при прежних
размере/mtime также исключает результат. Для области проверяется ревизия
вида. При построении хеш проверяется до и после вычисления. Прежние записи
сохраняются как производная история, автоматической очистки пока нет.

## Выдача и ограничения

Однословные марки с цифрами (`Н-1`, `QF1`) используют точные FTS-термы даже
при выбранном смысловом режиме. Для марки дополнительно проверяется буквальная запись с границами,
чтобы `Н-1` не приравнивалась к `Н 1` или `Н-1.1`. Остальные запросы — AND
термов без русского стемминга. Совмещённый режим объединяет ранги точного
и смыслового поиска; близкие и перекрывающиеся фрагменты могут повторяться.

Если worker не настроен, индекс пуст, модель изменилась или worker отказал,
возвращается **явный переход на точный поиск** с причиной. Поиск только по
смыслу также сообщает такой переход. Длинный запрос сверх байтового бюджета
нужно сократить. Зависшие/неверные ответы worker ограничены таймаутом,
проверяются размеры, ID ответа, конечность и ненулевой вектор.

Порог cosine **0,72 — предварительный фильтр кандидатов**. Он выбран после
малого текстового smoke-прогона; не откалиброван для полного русского ПД/РД
и изображений. Его можно менять параметром MCP `min_similarity`.
Он не означает вероятность правильного ответа. Пустая выдача не доказывает
отсутствия данных; высокая близость не доказывает соответствие оборудования.
Смысловой поиск не сверяет количества и не создаёт принятых фактов.

Сравнение векторов сейчас линейное по подготовленной части одного проекта;
ANN/векторного сервера нет. Векторы — 1536 байт на 768-мерный сегмент без
накладных расходов SQLite и текста. Два процесса (индексатор и запросы)
освобождают модель после двух минут простоя. Индексатор считает фрагменты
по одному; подготовка большого комплекта может занять заметное время.
На публичном статическом демо Python-worker не запускается.

## Проверено 25.10.2026

Выполнен запуск Windows helper с закреплёнными весами. На 6 синтетических
русских инженерных текстах: 5/5 перефразированных запросов дали нужный документ
первым в semantic/hybrid; literal с теми же полными формулировками — 0/5.
Два отрицательных запроса при 0,72 не дали кандидатов. Это тот же малый корпус,
на котором выбирался порог, **не независимая оценка качества**. Проверяемый запуск:

```powershell
python tools/evaluate_semantic_search.py --home C:\ProjectMemory --output C:\SearchSmokeRun
```

[Полный синтетический отчёт](benchmarks/embeddinggemma-windows-smoke.json)
содержит 9 запросов × 3 режима. С учётом марки кабеля и ID:
literal top-1 — 2/7 положительных запросов, semantic — 6/7, hybrid — 7/7.
Смысловой режим пропустил точное обозначение кабеля при выбранном пороге;
совмещённый нашёл его через FTS. Время измерено с прогретым файловым кешем
при общей нагрузке на компьютер; результаты не являются воспроизводимой
оценкой производительности.

- Синтетический PDF с явно сохранённой областью прошёл настоящий image
  pipeline: текст и область получили отдельные векторы и точные локаторы.
  Для русского запроса к английской схеме cosine области 0,655 — ниже
  стандартного порога. Качество поиска по чертежам этим не подтверждено.
- Регрессионные тесты используют отдельный явно синтетический worker:
  проверяют протокол, возобновление, несколько фрагментов одного файла,
  версии/проекты, исходник с изменёнными байтами и обновлённую область PDF.
  Эти тесты не измеряют качество модели.
